# عقد الـAPI: المستندات والتحميل بالـscroll

كل الطلبات تحتاج `Authorization: Bearer <accessToken>`.
المستندات مشتركة داخل مساحة الشركة المصرّح بها، والمحادثات والرسائل خاصة بمالك المحادثة.

## المستندات: بحث وفلاتر وصفحات

```http
GET /api/documents?page=1&limit=1&search=Orion&status=ready&fileType=pdf
```

| المعامل | الافتراضي | السلوك |
|---|---|---|
| `page` | `1` | رقم الصفحة، من 1 إلى 1000000 |
| `limit` | `20` | عدد المستندات، من 1 إلى 100 |
| `search` | فارغ | جزء من اسم الملف، دون حساسية لحالة الأحرف، حتى 200 حرف |
| `status` | دون فلتر | `queued`, `processing`, `ready`, `failed`, `cancelled` |
| `fileType` | دون فلتر | `pdf`, `docx`, `xlsx`, `xls`, `csv`, `md`, `txt` |

الفلاتر تعمل معًا بـAND. لإلغاء فلتر الحالة أو النوع، احذف المعامل من الطلب.
`fileType` يقبل أيضًا مثل `.PDF` ويُرجع القيمة الموحدة `pdf`.
البحث نص حرفي في **أسماء الملفات**؛ `%` و`_` لا يعملان كـwildcards.
للبحث داخل محتوى المستندات، يبقى `POST /api/documents/search` هو مسار TypeGraph المستقل.

الاستجابة التالية مثال بحد مستند واحد، مع اختصار حقول المستند المعروضة:

```json
{
  "documents": [
    {
      "id": "00000000-0000-4000-8000-000000000001",
      "filename": "Orion.pdf",
      "fileType": "pdf",
      "status": "ready",
      "fileSize": 12000
    }
  ],
  "meta": {
    "page": 1,
    "limit": 1,
    "count": 1,
    "total": 21,
    "totalPages": 21,
    "hasNextPage": true,
    "hasPreviousPage": false,
    "filters": { "search": "Orion", "status": "ready", "fileType": "pdf" }
  }
}
```

- `total` و`totalPages` محسوبان بعد تطبيق البحث والفلاتر وداخل مساحة الشركة فقط.
- `count` هو عدد العناصر في الدفعة الحالية. عند عدم وجود نتائج: `documents=[]`, `total=0`, `totalPages=0`.
- الترتيب: `createdAt DESC, id DESC`. الإجمالي والصفحة يُقرآن في transaction واحدة ذات snapshot ثابت للطلب.
- عند تغيير البحث أو الفلاتر، ابدأ من `page=1`. الطلب التالي يستخدم `page+1` مع الفلاتر نفسها.
- القائمة تعدّ المستندات المنطقية، وليست النسخ أو المقاطع. الحالة واسم الملف يعكسان سجل المستند الحالي؛ تفاصيل النسخ في مسارات `/versions`.
- **تغيير شكل الاستجابة:** كان `GET /api/documents` يرجع array مباشرة؛ الآن اقرأ `response.documents` و`response.meta` في الفرونتند.
- القيم غير الصحيحة أو المتكررة، والمعاملات غير المعروفة، ترجع HTTP400.

## قائمة المحادثات: cursor للـinfinite scroll

```http
GET /api/agent/conversations?limit=2
```

```json
{
  "conversations": [
    { "id": "00000000-0000-4000-8000-000000000002", "title": "Orion", "lastMessage": null },
    { "id": "00000000-0000-4000-8000-000000000001", "title": "Costs", "lastMessage": null }
  ],
  "meta": {
    "limit": 2,
    "count": 2,
    "hasMore": true,
    "nextCursor": "00000000-0000-4000-8000-000000000001",
    "direction": "older"
  },
  "hasMore": true,
  "nextCursor": "00000000-0000-4000-8000-000000000001"
}
```

المثال يختصر بقية حقول المحادثة مثل التوقيتات. الدفعة التالية:

```http
GET /api/agent/conversations?limit=2&cursor=00000000-0000-4000-8000-000000000001
```

الافتراضي 50 محادثة، والحد الأقصى 100. الترتيب حسب آخر تحديث من الأحدث للأقدم ثم `id`.
`direction=older` يصف اتجاه طلب الدفعات الأقدم، وليس حدث scroll من السيرفر.
الحقول القديمة `hasMore` و`nextCursor` في المستوى الأعلى باقية للتوافق؛ يفضّل استخدام `meta`.

## رسائل محادثة واحدة: تحميل الأقدم عند الوصول للأعلى

```http
GET /api/agent/conversations/00000000-0000-4000-8000-000000000001?limit=2
```

الطلب الأول يختار أحدث رسالتين، ويعرضهما داخل الدفعة من الأقدم للأحدث:

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "messages": [
    { "id": "10000000-0000-4000-8000-000000000001", "role": "user", "content": "السؤال" },
    { "id": "10000000-0000-4000-8000-000000000002", "role": "assistant", "content": "الإجابة" }
  ],
  "meta": {
    "limit": 2,
    "count": 2,
    "hasMore": true,
    "nextCursor": "10000000-0000-4000-8000-000000000001",
    "direction": "older"
  },
  "hasMore": true,
  "nextCursor": "10000000-0000-4000-8000-000000000001"
}
```

عندما يصل scroll إلى بداية المحادثة، أرسل نفس المسار مع `cursor=meta.nextCursor`، ثم أضف `olderResponse.messages` **قبل** الرسائل الموجودة.
الافتراضي 100 رسالة، والحد الأقصى 200. الحد يعدّ الرسائل، وليس أزواج السؤال/الإجابة.
حد العرض مستقل عن عدد الرسائل التي يرسلها الباكند إلى النموذج كسياق.
Cursor الرسالة يخص هذه المحادثة فقط؛ cursor من محادثة أخرى يرجع404.

## ربط أحداث الـscroll في الفرونتند

1. احتفظ بحالة cursor مستقلة لقائمة المحادثات، وبحالة مستقلة لرسائل كل conversationId.
2. في أول طلب لا ترسل cursor. لا تحسبه من آخر عنصر معروض؛ استخدم `meta.nextCursor` كما هو.
3. لا تطلب دفعة أثناء وجود طلب جارٍ. توقف عندما `meta.hasMore=false` و`nextCursor=null`.
4. للرسائل: عند scroll للأعلى حمّل الأقدم وأضفها في البداية، مع الحفاظ على موضع العنصر المرئي بعد الإضافة.
5. لقائمة المحادثات: الدفعات الأقدم تُضاف في النهاية عند العرض بالأحدث أولًا. إذا أردت عرض الأقدم أولًا والتحميل من الأعلى، اعكس ترتيب كل دفعة وأضفها في البداية.
6. امنع التكرار بواسطة `id`. عند تبديل المحادثة لا تستخدم cursor المحادثة السابقة.
7. عند وصول تحديث يحرك محادثة إلى أعلى القائمة، أعد تحميل أول دفعة؛ `updatedAt` قابل للتغير، وهذه ليست snapshot ممتدة عبر طلبات متعددة.
8. عند فشل طلب دفعة، احتفظ بالبيانات والـcursor الحاليين لإعادة المحاولة. لا تمسح سجل المحادثة.

هذه طلبات HTTP عادية تُستدعى من حدث scroll في الواجهة؛ لا تحتاج SSE جديدًا للـpagination.

## التحقق

```bash
npm run typecheck
npm run typecheck:audit
node --import tsx --test test/document-list-http.test.ts test/agent-reliability-http.test.ts
npm test
```

اختبارات HTTP تستعمل controller/service/guard حقيقية مع هوية اختبار وPrisma بديلة في الذاكرة.
تغطي الفلاتر والإجماليات والصفحات والـmeta وعزل الشركة وملكية المحادثات والتحقق من المعاملات.
ليست هذه الاختبارات إثباتًا لسلوك collation أو isolation على PostgreSQL الحي.
